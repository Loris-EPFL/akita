# Akita: fitting upstream 275 / ordinary-extension reference investigation

## Decision

**The strongest fitting upstream base is cached `origin/quang/sis-profile-q128-offset275` at `b43726232e0d40cd9c144dfabb6858be7aeebd1d`, not an old default-275 checkout.** It is exactly cached main `60b82bc30f4f8f1130ccd71fe10b0b9bed909ab9` plus `33583fbe6cb71d28c0f2366f44a20f798a04caec` (registered exact 275 SIS profile) plus `b437262...` (exact-modulus validation for in-memory commitments). This is a real upstream option, not merely a hypothetical change to dirty A7F7 types.

There is an important qualification: **this ref does not ship a production 275/Ext2 preset, a 275 schedule artifact, or a Main56/original-26-plane 275 extension roundtrip.** Its actual 275 end-to-end config explicitly sets `ExtField = Field` and tests a singleton Dense source at nv=14. The field/basis components and complete ordinary extension/recursive/batched pipeline exist, but their composition for this exact target remains an integration obligation. Thus the answer is “real supported fitting base, yes; already-complete target configuration, no.”

Selecting `K = Prime128Offset275` and `E = Ext2<K>` **before generating new experiment sources** removes the new NR5-to-ordinary-ring-basis bridge. This is a supported Akita modulus choice within its existing lattice-assumption family, not a new class of lattice assumption. It is nevertheless a different exact Module-SIS instance/profile, setup, arithmetic field and proof statement. **Never reinterpret or migrate the existing actual A7F7 commitments, source handles, planes, decoded memory, setup matrices, or transcript artifacts.**

## 4. Why default extensions fit 275, and why A7F7/NR5 does not

The pinned Jolt Solinas implementation documents that default `Ext2<F>` is `FpExt2<F, TwoNr>` (u²=2), and FpExt4/FpExt8 use the cyclotomic ring-subfield basis. They are fields exactly for q≡±3 mod8, including q275≡5. A7F7≡1 gives rings instead. [Pinned field declaration](https://github.com/a16z/jolt/blob/1618f4b6dc97effcec3568ca7cf2b7420ac9e75f/crates/jolt-field/src/solinas/mod.rs#L160-L168), [extension basis/alias](https://github.com/a16z/jolt/blob/1618f4b6dc97effcec3568ca7cf2b7420ac9e75f/crates/jolt-field/src/solinas/ext.rs#L1-L57).

[Actual `FpExtEncoding`](https://github.com/LayerZero-Labs/akita/blob/b43726232e0d40cd9c144dfabb6858be7aeebd1d/crates/akita-types/src/field_reduction.rs#L12-L66) means the coordinates consumed by Akita's ring-subfield embedding. Impl targets are base F, **default `Ext2<F>`**, FpExt4<F>, FpExt8<F>, not arbitrary `FpExt2<F,C>`. A7F7/NR5 is a genuine quadratic field but has the wrong multiplication/basis for that contract; adding a marker impl would not establish the embedding identities. NegOneNr does not fix A7F7 either. No already-supported true A7F7 ordinary-extension path was found in the inspected main, recursion, 275, dev-275 or focused Labinius sources. This is not a claim that other mathematical embeddings are impossible.

Modern Akita's extension role requires `ExtField<K> + MulBaseUnreduced<K> + Valid`, **not** Jolt's whole `JoltField` bundle. Pinned upstream solinas/ext.rs supplies extension arithmetic/CanonicalBytes, but does not supply its CanonicalEncoding/WithAccumulator frontend bundle there. The current dirty `jolt/crates/jolt-field/src/solinas/ext.rs` already has generic `CanonicalEncoding` and `WithAccumulator` impls for `FpExt2<Fp128<P>,C>`; these are reusable for q275/default TwoNr. Current compact-trace/RAM setup and opening-hint types still explicitly name A7F7/NR5 and need a coherent fresh-experiment cutover; they are not upstream evidence and must not be discarded.

## 5. Real ordinary extension pipeline and first-two-level policy

The first-two-level policy is not a blanket extension ban. [Catalog admission](https://github.com/LayerZero-Labs/akita/blob/b43726232e0d40cd9c144dfabb6858be7aeebd1d/crates/akita-schedules/src/resolve.rs#L27-L41) requires coefficient packing at fold levels 0 and 1. There is real full proof code, not just bounds: [coefficient-packing test](https://github.com/LayerZero-Labs/akita/blob/b43726232e0d40cd9c144dfabb6858be7aeebd1d/crates/akita-pcs/src/scheme/tests/coefficient_packing.rs#L137-L260) uses an fp32 degree-4 config, authenticated packing row, an actual recursive fold/setup prefix, retained private source, both polynomial bases, ordinary batched proving and verification. [Combined recursive setup test](https://github.com/LayerZero-Labs/akita/blob/b43726232e0d40cd9c144dfabb6858be7aeebd1d/crates/akita-pcs/tests/akita_small_field_e2e/combined_recursive.rs#L3-L104) invokes ordinary batched prove/verify through recursive extension-family setup. ## 6. Target source fit: Ext2 geometry yes; contracts still matter

The target recorded in current root notes is:

| Source | Logical polynomials / vars | Frozen A geometry | Original source digits | Frozen B |
|---|---|---|---|---|
| Main56 | 56 / 16 | dA128, B1, M512, rank3 | delta1; Boolean `UnitOneHot{chunk_size:1}` | width4368, rank1, d128 |
| RAM | 1 / 16 | dA128, B16, M32, rank3 | **all original 26 signed base32 planes** in [-16,15], including legal noncanonical paths | width1248, rank1, d128 |

Geometry is not the blocker for **Ext2**: [packing admission](https://github.com/LayerZero-Labs/akita/blob/b43726232e0d40cd9c144dfabb6858be7aeebd1d/crates/akita-planner/src/schedule_params/candidate/opening.rs#L27-L92) requires `k*s | dA` and `dD | k*s`; [checked geometry](https://github.com/LayerZero-Labs/akita/blob/b43726232e0d40cd9c144dfabb6858be7aeebd1d/crates/akita-params/src/layout/subring_packing_geometry.rs#L8-L81) has dA=k*h*s. Existing production [challenge dimensions](https://github.com/LayerZero-Labs/akita/blob/b43726232e0d40cd9c144dfabb6858be7aeebd1d/crates/akita-challenges/src/config.rs#L162-L179) start at64. Therefore **k2,s64,h1 gives width128 and stride2**, fitting dA128/dD128. This is a static geometry deduction, not a planned/audited complete schedule.

FpExt4/FpExt8 are also genuine fields and have the ordinary basis over 275, but at s≥64 their minimum widths256/512 do **not** divide the fixed dA128. They are not drop-in options for those original source shapes under the retained first-two-level policy.

Main56's chunk1 contract is a legal upstream class parameter but is not the stock OneHot policy: [standard presets](https://github.com/LayerZero-Labs/akita/blob/b43726232e0d40cd9c144dfabb6858be7aeebd1d/crates/akita-config/src/proof_optimized.rs#L50-L55) use chunk256. Nor is the 275 Dense test equivalent to these producers: it inherits basis3/full-field Dense rather than frozen original base32 planes and Main's Boolean contract. The target needs its own truthful producer contracts/keys, not renamed stock artifacts.

The exact raw26 contract is absent from upstream b437/recursion source inventories. [Committed source norm derivation](https://github.com/LayerZero-Labs/akita/blob/b43726232e0d40cd9c144dfabb6858be7aeebd1d/crates/akita-params/src/sis/committed_source.rs#L155-L220) only handles UnitOneHot and canonical declared-bound BalancedSignedDigit. For log_bound128/base32/delta26 it grants the final plane only three remaining bits: reach4, energy `25*256+16=6416` per coefficient. The original all26 full-width signed-plane contract needs `26*256=6656`. These are not interchangeable even though maximum individual reach is16 in both. A full-width source declaration/audit must not silently undercharge its aggregate energy or canonicalize its digits.

Private source support is real: [private_cpu test backend](https://github.com/LayerZero-Labs/akita/blob/b43726232e0d40cd9c144dfabb6858be7aeebd1d/crates/akita-pcs/tests/dynamic_backends/private_cpu.rs#L1-L39) privately retains commitment, recursive witness and material handles. [Owned opening](https://github.com/LayerZero-Labs/akita/blob/b43726232e0d40cd9c144dfabb6858be7aeebd1d/crates/akita-cpu-backend/src/opaque/owned.rs#L180-L346) obtains a source opening batch and coefficient-packing partials without replacing ownership with a decoded table. The position-source packing kernel accepts a coefficient callback. But a private handle seam alone does not implement original26 planes.

Relevant reachable existing dirty work: `akita/crates/akita-cpu-backend/src/sources/packed_ram.rs` stores original signed planes verbatim, commits/folds from the retained packed allocation and decodes requested coefficients on demand. Its current ordinary packing impl at lines382–427 is explicitly F/F, degree1, s128, stride1. Therefore changing setup field to275 alone does **not** activate E2 packing. The required source-kernel implementation is the analogous F/Ext2 retained-plane path with k2/s64/stride2 plus admission into ordinary source/fold/material handling, not a DensePoly/redecomposition fallback.

## 8. Performance and statement distinctions

- Eliminating NR5 bridge removes custom basis conversion/proof work, but Ext2 still has two base coordinates, extension multiplication, extension-valued sumchecks and possible later EOR. **[INFERENCE]** It may materially simplify the target; no numerical speedup is measured here.
- A7F7 was selected for smooth FFT/RS arithmetic. Switching to275 changes reduction/encoding/FFT behavior; 275 does not inherit A7F7's multiplicative subgroup. Existing old microbench records are not evidence of target-segment throughput. Compare accumulator and non-accumulator cases under the same275 setup rather than attributing all differences to accumulation.
- k2/s64 preserves dA128/dD128 and width128 but changes the subring challenge family/stride from native k1/s128. Rank/norm/alpha/grinding/tail cost must follow the actual selected schedule. k4/k8 would force a different source geometry/policy and therefore a different benchmark.
- An ordinary decoded-memory opening authenticates an algebraic claim about the retained source. It does not by itself prove each original RAM digit is in [-16,15] or prove frontend Boolean/application predicates. Relation soundness and raw-plane range/VM-execution soundness must be stated separately. Keeping original decommitments does not automatically add these predicates.
- The original-source/Jolt benchmark intent can be preserved for **fresh** q275 instances if the real trace/VM workload, Main56 and original-plane sources, endpoint identity and continuation/application constraints are recreated under that setup and the final reduction opens those retained sources through one ordinary batch PCS. A random Dense roundtrip, changed Main chunk policy, canonicalized RAM, verifier-in-Jolt guest alone, or scalar-only final relation is not that benchmark. If the benchmark specifically means the already-created A7F7 sources or byte-identical artifacts, q275 does not meet it; retain A7F7 and complete its real NR5 bridge/full-ring integration instead.
