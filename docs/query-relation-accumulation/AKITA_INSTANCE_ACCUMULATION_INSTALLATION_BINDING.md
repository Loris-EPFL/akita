# Selected expanded installation binding and unselected compact proposal

Status: the finite expanded resource contract below is selected for the prototype. Full current definition/event framing is preserved. The compact deterministic-derivation proposal remains an **unselected optimization**, requiring independent review before any cutover. Neither route establishes numerical security or parity.

## Observed failure

Before selecting the expanded resource profile, the real two-segment frontend driver failed installation admission before producing its frontend proof. Its first installation description had 7,917,436 bytes, exceeding the historical 4 MiB record limit. The observed constituents included 2,556,205 bytes of draw keys, 2,318,391 bytes of message keys and 109,543 bytes of exact payloads. Native plan binding had 6,173 bytes. Evidence: runtime artifact `artifact://1885`, generated by `cargo test -p jolt-prover --features akita,transcript-d1 --test akita_two_segments -- --ignored --nocapture`. The expanded profile still requires parent-owned compilation and execution.

The implementation serializes the full message/draw definition inventory and event grammar into each public installation context. Those inventories repeat fixed typed paths, codec descriptions, carry references and allowed compression branches. The historical compiler-total limit was 16 MiB. Raising only the record limit would not establish that two frontend/native transitions, their complete seals, native updates and final suffix fit the total limit. These bytes are an **installation description**, not a measured certificate size.

## Selected expanded resource contract

`jolt-verifier/src/segment_native_resources.rs` is the shared authority for this finite prototype profile:

| Resource | Selected cap |
| --- | --- |
| Segment count | 16 |
| Context, record payload, native seal, native event payload | 16 MiB each |
| Retained canonical transcript, including record headers | 512 MiB |
| Total records; streams per snapshot | $2^{20}$ each |
| Generated blocks per stream | 71 (derived conservative shell envelope) |
| Component calls; bits read across the session | $2^{24}$; $2^{28}$ |
| Schema nodes; depth | 131,072; 16 (unchanged) |
| Frontend coordinates; deterministic powers per draw | 256 each (unchanged) |

The 16 MiB payload cap gives conservative headroom above the observed 7,917,436-byte first context and the full native seal that embeds it. The 512 MiB session cap, rather than a payload-only repair, budgets retained frontend messages, repeated complete next-context publications, complete seals, native updates and suffix/terminal messages. The caps independently bound finite work and storage; they do **not** promise every possible 16-segment execution fits. Actual certificate bytes (frontend frames plus native proof messages) and retained transcript/absorption work must be measured separately.

Every selected cap is bound before challenges in the complete installation context. The original eight little-endian footer words retain their positions; the explicit `jolt/compact/expanded-native-resources/v2` suffix then binds segment count, snapshot-site cap, schema nodes and schema depth. Record/context/seal/event limits share one payload value. Registry admission requires the exact selected compiler/frontend caps, including `record_bytes == payload_bytes`; it cannot accept a looser or independently chosen contract. Frontend installation and native inventory reject more than 16 segments. All immutable definition keys, codecs, arities, carries and branch schedules remain fully serialized and enforced.

Native plan admission parses the actual installation prefix: the installation tag, the length-delimited RAM-contract identity, the immediately following native-plan tag, and its length-delimited plan field. It compares that field directly against the expected plan; an expected marker embedded later in public IO cannot substitute for a wrong actual plan. This prefix check deliberately does not replace the trusted constructor's enforcement of the remaining complete definition grammar.

The selected K modulus is `d1::Q = 340282366920938463463374607427473266697`. Frontend definition construction and the resource decoder share `d1::K_FAMILY`; the resource report derives its decimal string from `Q`. Earlier labels/report metadata incorrectly advertised a modulus larger by 1,024. This correction changes metadata, not the actual field arithmetic, sampler, or literal extraction-tree modes.

The initial zero receiver is constructed in `FullRingAccumulationPlan::new` with the live terminal compression-map dimension, matching the actual CPU producer. For this selected profile the public `p_F` has eight K coefficients in dimension eight; this is the prescribed compressed terminal payload, not the original native128 source ring. Wire decoding may use `RingVec` compact dimension zero because the frozen profile supplies the terminal geometry externally. That wire convention must not make the installed live zero commitment differ structurally from its real producer. Source handles, coefficient values, profiles, equality checks, and retained compression material are unchanged.

The H1610 compiler charges one component absorption per complete 64 canonical record bytes, plus snapshot finalizations and generated tape blocks. The component/read caps are explicit additional abort boundaries. The v2 stream cap is derived from the conservative shell envelope $40\cdot256\cdot7+40=71{,}720$ bits, rounded up to 71 blocks; the width-128 first draw always accepts, so that envelope is conservative. This removes the former 64-block premature compiler cutoff without changing the 256 attempts per draw or forty sign bits. The changed bound/tag is bound before challenges and changes transcript bytes. It does not prove the full conditional-answer law or numerical security.

Receipt/archive policy remains externally supplied. Standalone transport uses checked finite total budgets and u32-representable component budgets; the optional VM wrapper's 1 GiB I/O ceiling is not imposed on the native certificate. A further ordinary Akita or SNARK wrapper is optional and unselected. This resource profile is neither a security threshold, a numerical admission, nor a measured receipt-size assertion; `numerical_security_admitted` remains false.

## Actual integration driver and ordinary control

`jolt/crates/jolt-prover/tests/akita_accumulation.rs` uses the public canonical accumulation-plan constructor and transports two complete `NativeFrontendFrame` records, including their public contexts, separately from the native stream inside the canonical archive. The concrete shape-aware codec derives its frontend dimensions from approved configuration and full-public preprocessing. The public native certificate verifier reconstructs every frontend/source/Common-K claim, consumes both root updates, the final domain/normalization, all three recursive suffix rows, terminal equations and exact EOF. The ignored test also exercises changed statements/frame chains, changed frontend/native/terminal messages, truncation and trailing bytes through the public codecs and verifiers. New driver revisions require execution by the integration owner; code presence is not a passing test report.

The same fixture provisions one matrix prefix covering the installed native catalog and the independently frozen `OrdinaryControl` row. The ordinary comparison generates its own two frontends over the same actual witnesses, including each path's original Main commitment creation. It compares original Main commitment metadata/payload and every physical source coefficient against the retained native originals. Original signed/noncanonical RAM handles are reused without decoding/recommitting their sources. Each ordinary verifier independently reconstructs the Common-K 56-column endpoint and two RAM leaves, rebuilds a session binding the complete public statement and its own canonical frontend records, and runs the complete ordinary PCS verifier. It does not replay a native root prefix.

The ordinary PCS boundary reverses all three authenticated Jolt/MSB-first points into the backend's low-bit-first convention, without changing their evaluations, commitments, or original source handles. In particular, `PendingMainNormalization.ordinary.point` is the reversed logical prefix of its low-first `raw_point`; it must not be passed directly to the ordinary opening engine. Independent original `main_values`/`ram_value` checks evaluate all three groups at the admitted PCS coordinates before proving, and the Main point is checked against `raw_point[..16]`.

Measurements distinguish shared setup, each path's frontend and complete PCS work, cross-path source checks, native archive bytes, ordinary frontend component bytes, complete ordinary PCS proof bytes, and public statement bytes. The ordinary control consists of two independent complete segment proofs, not an unavailable ordinary outer recursive zkVM aggregator or a separately specified aggregate-certificate codec. Neither these differing proof boundaries nor the source checks establish full end-to-end performance/security parity. The driver reports `optional_wrapper=false`, `ordinary_outer_aggregator=false`, and `parity=false`, and emits the actual ordered composed prerequisite inventory without numerical admission.

Set `AKITA_RESOURCE_REPORT=/tmp/akita-composed-resources-v2.json` when running the ignored integration test to persist the complete composed prerequisite report. The driver streams it through a buffered JSON writer and propagates creation/serialization/flush errors; it does not allocate a second multi-megabyte JSON string. Stdout contains the actual artifact path/byte length, concise inventory counts, matrix targets and missing-prerequisite identifiers rather than the full report. With the environment variable unset, only those summaries are printed.

## Unselected compact deterministic-derivation proposal

Let $G_v$ be the trusted, deterministic schema derivation algorithm for a versioned, selected profile. Let $x$ be its complete derivation input. Installation computes

$$
\mathcal D = G_v(x), \qquad I = \operatorname{Encode}(v,x),
$$

where $\operatorname{Encode}$ is canonical, injective and length-delimited. The proposal binds $I$ to the existing compiler instead of serializing every derived definition again. No new hash or digest substitutes for any input. The existing transcript compiler and its assumptions remain unchanged.

This is valid only if the following invariant is proved from the implementation:

$$
(v,x)=(v',x') \implies G_v(x)=G_{v'}(x').
$$

Equality on the right includes every allowed message occurrence, message kind, codec, count, exact payload, compound scope, draw occurrence, sampler, challenge field, tree mode, arity, carry projection, powers bound, compression choice and chronological event branch. It does not mean merely equal numbers of records.

### Complete input obligations

The input encoding must include or canonically determine:

1. Protocol/schema-derivation version and supported compilation/field axes. Different conditional schema code must not share the same identifier without an explicit equivalent-schema proof.
2. The authenticated full setup/source descriptor and selected frozen schedule/native accumulation plan binding, including total updates. A layout digest alone is insufficient.
3. Actual frontend configuration: one-hot and read/write geometry, trace order, bytecode size, and all parameters used by roster construction.
4. Checked public preamble and complete public segment context: run identity, preprocessing identity, IO and panic state, segment index/count, active/padded rows, expanded counts, start/end/successor state, registers and any enabled field-register state, and original incoming/outgoing RAM commitments and their complete contracts.
5. Main source-check geometry, column map and zero/PC obligations, and the original Main view/commitment shape used by normalization.
6. Every finite compiler, record, sampler, schema and native resource bound. Bounds remain checked; smaller framing is not an excuse to omit them.

A value already emitted later may determine an adaptive proof record, but may not silently determine the earlier installation grammar. For example, the actual Main commitment is unknown when installation is derived. Its exact allowed shape is installed; its complete actual value must still be emitted before the frontend challenges. Normalization claim values likewise remain actual proof messages before normalization coefficients.

### Enforcement obligations

The immutable derived registry must still reject every uninstalled definition and enforce the full chronology, aliases and branch choices. Native transitions must authenticate the exact next $I$ before granting a K frontend loan. The same compiler must survive every transition. The full seal must authenticate the actual emitted claims and original commitments; it must not accept the compact installation encoding as a substitute for those claims.

All prover and verifier callers must use the new version together. No legacy framing alias or fallback is allowed. A parameter missing from $x$ is a protocol defect, not an acceptable optimization.

## Soundness scope

The relevant argument is trusted deterministic derivation, not collision resistance of a new compression function. Under injective encoding and the derivation invariant, an attacker cannot choose a second accepted definition inventory for the same installed input. Its accepted frontend/native executions therefore obey the same relation and finite branching program used by the soundness and resource analysis.

This does **not** establish the complete composed extractor/runtime certificate, QROM security, or performance parity. The current artifact remains structurally admitted only. The full finite event/carry inventory remains available to accounting and review even when it is not repeated as public transcript data.

## Review required before selecting the compact proposal

Before implementation: independently audit every constructor input and conditional code path against the encoded $x$, plus registry enforcement and next-context authorization. Check field-register context coverage explicitly.

After implementation: execute the real two-segment frontend; measure actual installation, seal and retained transcript sizes; execute the complete native updates/final decider; validate the composed runtime accounting; exercise altered derivation inputs and framing/EOF failures through the real verifier. Do not declare the final receipt or parity complete from installation success alone.
