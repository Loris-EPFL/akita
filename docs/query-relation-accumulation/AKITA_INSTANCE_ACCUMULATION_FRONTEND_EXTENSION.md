# Native Jolt source/challenge-field separation audit

## 1. Verdict and immutable source identity

All J: paths below mean Jolt **0791f79a55c3fadc3d327c78a72228696c338468**; A: means Akita **83574331d4e51f8cce1d8689d05592fa4ef4c138**. Sources were retrieved from those immutable trees/raw URLs, not the differing working heads. The actual field implementation is **J:crates/jolt-field/**. Jolt’s [root Cargo.toml](https://github.com/a16z/jolt/blob/0791f79a55c3fadc3d327c78a72228696c338468/Cargo.toml) patches the Git-source jolt-field and jolt-poly packages to its workspace members and pins Akita to A. J:crates/jolt-akita/Cargo.toml directly enables the sibling jolt-field’s solinas feature.

J:crates/jolt-akita/src/adapters.rs defines `AkitaField = akita_config::proof_optimized::fp128::Field`. A:crates/akita-config/src/proof_optimized/fp128.rs aliases that field to `Prime128OffsetA7F7`; J:crates/jolt-field/src/solinas/mod.rs defines it as `Fp128<0xFFFF_A7F7>`, i.e. q=2^128−2^32+22537. The native fp128 Dense, DenseBounded and OneHot presets pass **Field, Field** as base/evaluation field parameters: they do not select the proposed quadratic E.

**[INFERENCE—algebraic conclusion]** For a fixed K-valued Boolean table w and a polynomial identity P over K, injectivity of K→E gives P(w)=0 iff its embedded identity holds in E. Its multilinear extension is naturally evaluated at r∈E^n by Σ_x ι(w_x)eq_E(x,r). Thus larger challenge points do not inherently require larger committed source coefficients, changed VM arithmetic, or new source planes. This is a candidate extension-lift lemma, **not** an existing end-to-end frontend API or a proof that every existential auxiliary witness over E descends to K.

## 2. Field and encoding: what is mathematical, what is a type barrier

* **Reusable quadratic arithmetic exists.** [J:extension.rs](https://github.com/a16z/jolt/blob/0791f79a55c3fadc3d327c78a72228696c338468/crates/jolt-field/src/extension.rs) exposes `Ext2Config<F>` with a generic nonresidue path. [J:solinas/ext.rs](https://github.com/a16z/jolt/blob/0791f79a55c3fadc3d327c78a72228696c338468/crates/jolt-field/src/solinas/ext.rs) implements `FpExt2<F,C>` arithmetic, inverse via conjugate/norm, coefficientwise `Field::random`, `ExtField<F>::lift_base`, `mul_base`, coefficient access and Frobenius. `CanonicalBytes` encodes c0||c1; serde is coefficientwise. A nonresidue-5 configuration can reuse these formulas. No new modulus is needed.
* **The default extension is wrong for this K.** `FpExt2<F>`/`Ext2<F>` default to `TwoNr`. The source explicitly states that 2 is square for Prime128OffsetA7F7 (q≡1 mod 8), so this default is not a field there. Merely choosing `Ext2<AkitaField>` is unsound. The generic implementation’s Rust `Field` bound does not certify irreducibility of an arbitrary configuration. The profile supplies the nonsquare-5 premise; it must be attached to the selected type/configuration.
* **JoltField is not intrinsically a prime-field trait.** [J:algebra.rs](https://github.com/a16z/jolt/blob/0791f79a55c3fadc3d327c78a72228696c338468/crates/jolt-field/src/algebra.rs) defines the blanket `JoltField` bundle from `Field + CanonicalEncoding + WithAccumulator + serde + MaybeAllocative`. `CanonicalEncoding::to_u128_checked` explicitly says that an extension returns its constant coefficient only when higher coefficients vanish. It would be incorrect to claim that all frontend algebra requires arkworks `PrimeField`.
* **Nevertheless E does not acquire the production bundle by aliasing F.** The inspected FpExt2 implementation supplies `CanonicalBytes`, not the full `CanonicalEncoding`/JoltField bundle. [J:solinas/unreduced.rs:648–721](https://github.com/a16z/jolt/blob/0791f79a55c3fadc3d327c78a72228696c338468/crates/jolt-field/src/solinas/unreduced.rs#L648-L721) already supplies `Unreduced`, `MulBaseUnreduced` and `Fold` for configured Fp128 quadratic extensions; those are immediate-reduction identity implementations, not a production `WithAccumulator` bundle. The latter separately serves generic kernels' `fmadd_i64`, `fmadd_u64`, signed and wider source products. Supply the E capabilities actually consumed or narrow challenge-side bounds. `Unreduced` and `WithAccumulator` must not be conflated.
* **Genuine prime-field/source semantics stay at K.** J:solinas/fp128.rs has canonical 16-byte integers, checked representative conversion, modular byte reduction and scalar decode. A’s source decomposition and centered-bound calculations consume K residues/modulus and signed digits. Those are not meaningful as “one integer residue modulo |E|” for arbitrary E elements and must not be redirected to E. Conversely `from_u64`, `from_i64`, powers of two and fixed interpolation nodes can be embedded in E without altering their characteristic-q meaning.

## 4. Challenge-dependent operation classification

### Polynomial arithmetic and reusable kernels

**[INFERENCE]** Addition/multiplication, equality polynomials, multilinear interpolation/binding, integer-node univariate interpolation, symbolic constraints and RLCs commute with embedding of K coefficients. Their formulas can remain unchanged.

Concrete reuse evidence:

* J:crates/jolt-claims/src/symbolic.rs: `SymbolicSumcheck` exposes field-generic expressions for fixed relation geometry; J:sumcheck.rs describes Boolean and centered-integer domains.
* J:crates/jolt-sumcheck/src/prover.rs: `ProveRounds<F>`, batch/uni-skip engines use algebraic `Field`-level operations. `tests/extension_fields.rs` contains actual quadratic/quartic extension sumcheck test code; it demonstrates intended generic engine support, **not** a compiled or exercised K/E Jolt frontend.
* J:crates/jolt-poly/src/eq.rs, lagrange.rs, univariate.rs and split_eq.rs provide reusable equality/interpolation arithmetic. Dense/one-hot/equality routines can run on E-valued working tables once capabilities are satisfied.
* J:crates/jolt-openings/src/prefix.rs: `PrefixPacking::reduce_evaluations` forms Σ eval_i·eq(selector,i); `reduce_claims` absorbs layout/point/evaluations before sampling selectors. This algebra works in E, with physical source padding and layout still certified over K. It is explicitly a common-point fixed-prefix API, **not** an arbitrary multipoint normalization API.

**API barrier:** [multilinear.rs](https://github.com/a16z/jolt/blob/0791f79a55c3fadc3d327c78a72228696c338468/crates/jolt-poly/src/multilinear.rs) has `MultilinearEvaluation<F>::evaluate(&[F])->F`, `MultilinearBinding<F>::bind(F)` and `MultilinearPoly<F>` returning `[F]` source rows and folding by `[F]` weights. It cannot express borrowed K source rows with E evaluation/fold output. After the first nonbase challenge, bound values generally lie in E. A mixed-source evaluator/binder or explicit K→E working-state boundary is needed; changing the source table’s type to E would erase the separation being required.

Optimized kernels need separate attention even when formulas are valid: J:crates/jolt-kernels/src/optimized/spartan_outer.rs uses `SmallScalarAccumulator`, `SingleProductAccumulator` and signed/wide integer source operands; optimized inc/precommitted reductions combine row stores, challenges and `JoltWitnessPlane<F>` under one F. Base-only source processing may stay unchanged, but its challenge-weighted accumulators must output E.

### Fixed-table lookup and evaluation

[J:lookup traits](https://github.com/a16z/jolt/blob/0791f79a55c3fadc3d327c78a72228696c338468/crates/jolt-lookup-tables/src/traits.rs) separates `LookupTable::materialize_entry(index:u128)->u64` from `evaluate_mle<F,C>(r:&[C])->F`. For example signed-less-than uses integer sign/bit operations when materializing entries, but a polynomial in challenge coordinates during MLE evaluation; range-check MLE forms a sum of embedded powers of two times coordinates.

**[INFERENCE]** No ordering or bit decomposition of an E challenge is needed for these lookup MLEs. Keep original integer-indexed Boolean tables and interpret their MLEs in E. However `challenge_ops.rs::ChallengeOps<F>` requires challenge/challenge and mixed operations to return **F**. Its two parameters do not implement K-source/E-result evaluation. Taking F=K,C=E does not work; take the algebraic result field as E and separately preserve the original source materialization over K. Stage5 `InstructionReadRaf::derive_output_term` currently calls `evaluate_mle::<F,F>`.

### Inverses and excluded/exceptional points

* `lagrange_evals<F:Field>` explicitly handles r equal to an interpolation node with a one-hot result before dividing. Node-difference inverses are constants; the small integer domains remain distinct because characteristic remains q. No global resampling exclusion is implied here.
* The pinned `GruenSplitEqPolynomial::{gruen_poly_deg_3,gruen_poly_from_evals,gruen_poly_deg_2,recover_q_zero,zero_round}` has exact endpoint callbacks and zero-scale branches. Preserve them. [The complete audit](AKITA_INSTANCE_ACCUMULATION_FRONTEND_DESCENT.md), §5, proves that they return the same polynomial at every E point; no new exclusion or error charge is needed.
* Booleanity and instruction-RA gamma unscaling retain unscaled disabled-column openings at gamma zero. Their message paths omit only zero-weight terms. The inactive-round inverses are in `optimized/read_write.rs::RamAddressKernel`, not `lazy_ra.rs`; their denominators are the fixed nonzero constants 2 and powers of 2. These are total algebraic implementations, not random bad events. Keep their actual error propagation and full original gamma degrees.
* The field-inline inverse instruction is an **execution** constraint (`FieldRs1Value·FieldRdValue=1`), not challenge sampling. It remains an equation on K values embedded in E.

No inspected operation requires inventing an order on E. But totalizing a division, changing an error into zero, or adding a rejection filter would alter the protocol and requires its own argument; the lift must preserve the source’s actual behavior.

### Integer/byte conversions and source data

Shape arithmetic—arity, address indices, trace order, source lane IDs, byte counts, u64 words—is not migrated. Public integer/field-register endpoints are canonical K values per the segment contract, and RAM endpoints are full-field K; an honest u64 producer does not prove all algebraically valid cut states are u64.

[J:field-inline witnesses](https://github.com/a16z/jolt/blob/0791f79a55c3fadc3d327c78a72228696c338468/crates/jolt-witness/src/field_inline/witnesses.rs) is an important semantic boundary: `decode_value<F>` uses an optimized u64 path or `F::from_bytes_le_reduced`; `FieldRdInc` subtracts decoded post/pre values. `FieldProduct` and `FieldInvProduct` are likewise witness-field arithmetic. Decode/derive with **K**, then lift. Do not reinterpret the 32-byte `FieldEncodedValue` execution buffer as two E coefficients or reduce execution values modulo a fictitious integer |E|.

[J:field_constraints.rs](https://github.com/a16z/jolt/blob/0791f79a55c3fadc3d327c78a72228696c338468/crates/jolt-claims/src/protocols/composed/r1cs/field_constraints.rs) supplies guarded add/sub/mul/inverse/equality/zero/load equations and radix 2^64. Its FieldAdviceLimb row explicitly says the quotient is a **field quotient**, while canonical integer readout requires guest checks. Extension lifting does not license strengthening that row into integer division or dropping existing guest checks.

Committed program remains K-source data: J:crates/jolt-kernels/src/committed_program.rs materializes bytecode flags/one-hots, embedded PC/immediates, and padded u64 program-image words. J:optimized/precommitted_reduction.rs evaluates advice/program tables with equality/shifted-equality weights and carries reductions across stages6b/7. Only those weights, reduced states and evaluations become E; source role/layout and original handles do not change. On Akita, advice follows the stage4→stage8 direct-claim path, not the non-Akita stage6b/7 path.

## 5. Transcript sampling, serialization, and grinding

There is a concrete entropy barrier independent of Rust typing. [J:digest.rs](https://github.com/a16z/jolt/blob/0791f79a55c3fadc3d327c78a72228696c338468/crates/jolt-transcript/src/digest.rs) draws **16 bytes** for both `challenge()` and `challenge_scalar()` and then calls the selected field decoder. J:legacy.rs’s SpongeTranscript facade does likewise. J:solinas/fp128.rs’s scalar path uses modular byte reduction. A larger output type alone therefore does not sample uniformly from a field of size q²; at most 2^128 outputs are reachable from one unchanged draw. Nor is current modular reduction automatically exact uniform sampling over K.

`Transcript` itself permits a distinct associated `Challenge`, but callers constrain `T:Transcript<Challenge=F>`. Stage1/2 uni-skip code also intentionally distinguishes `challenge()` from `challenge_scalar()` (`draw_spartan_product_tau_high` documents this byte-compatibility distinction). Stage6a/6b share draws and Stage4/6b curate absorption aliases. A migration must enumerate these actual sites, not count one generic “challenge per round.”

Reusable native machinery exists: [A:proof_stream.rs:596–619](https://github.com/LayerZero-Labs/akita/blob/83574331d4e51f8cce1d8689d05592fa4ef4c138/crates/akita-transcript/src/proof_stream.rs#L596-L619)::`ext_challenge<F,E,S>` samples DEGREE base coefficients with separate `ProtocolSiteId.limb` records; `proof_stream/sampling.rs` supplies canonical rejection sampling. **Those site records are diagnostic, not absorbed domain separation** (`proof_stream.rs:662–686`). The selected new compiler must bind its actual framed namespace/sites. The current rejection loop is unbounded; `FIELD_SAMPLING_QUERY_LIMIT` is a protocol query budget, not a retry cap. The bounded candidate order, exhaustion error and complete accounting are new profile obligations. Coordinatewise extension codecs/sampling are reusable primitives, not evidence that Jolt's facade already implements the required protocol.

J:adapters.rs::`bridged_akita_session` currently ends the outer transcript with one `AkitaField` scalar and appends its bytes to the nested session domain. It also needs an explicitly versioned E/full-state binding policy compatible with the selected manifest; changing a generic alias is not enough.

Native grinding is distinct: A:proof_stream.rs implements bounded-u32-nonce preview/search/commit/receive and byte predicate challenges, with protocol context records. These are byte/integer operations, not extension-field arithmetic. They must retain their actual replay/filter/work accounting. Native grinding or a 128-bit security constant cannot retroactively turn earlier 16-byte/base-field frontend challenges into uniform E challenges. No new grinding theorem is established by this investigation.

## 6. Source/PCS/Akita boundaries requiring separate interfaces

1. **Proof and preprocessing types.** J:verifier/proof.rs has `JoltProof` stages/claims over `PCS::Field` and `VC:VectorCommitment<Field=PCS::Field>`. Top-level Akita prover bounds similarly equate witness field, PCS field, VC field and transcript challenge. A transparent E frontend still encounters these compile-time equalities even though no ZK claim is requested.
2. **Kernel/source access.** `SumcheckKernel<F>`, `ConcreteSumcheck<F>` and generated stage claim types can represent E proof algebra, but prepare/backend slots presently take `JoltWitnessPlane<F>` and F-valued source-derived buffers. Preserve `Witness<K>` separately from E points/claims/carries. Generated claim/point order is reusable; the witness-facing seam is not already mixed-field.
3. **PCS trait.** [J:schemes.rs](https://github.com/a16z/jolt/blob/0791f79a55c3fadc3d327c78a72228696c338468/crates/jolt-openings/src/schemes.rs) has one `CommitmentScheme::Field` for `commit<P:MultilinearPoly<Field>>`, opening point/value, grouped claims and transcript. Needed capability: commit/retain an original K source, then open or return a pending obligation at an E point with E values. `prove_batch` deliberately takes retained hints and no replacement polynomial—preserve that original-state contract.
4. **Concrete Jolt adapter.** J:scheme.rs fixes `type Field=AkitaField`; adapters.rs fixes dense/one-hot polynomials and commitment payloads to K. `reverse_point(&[AkitaField])`, ordered evaluations, native group structures and the session bridge are K-typed. Reordering itself is field-independent, but the signatures and codecs need separation. Jolt uses big-endian Boolean indexing while Akita uses little-endian indexing; the existing evaluation bit-reversal **and** point reversal must remain paired for E too.
5. **Custom one-hot source opening.** J:trace_onehot/opening.rs supports `OpeningFoldPlan::Base` with K scalar weights and a `Subfield` variant with `CyclotomicRing<K,D>` weights. It has no scalar-E/full-ring-two-plane branch. Unit one-hot source emission and short-source decomposition can remain K, while opening-fold outputs need the proposed plane-aware interface.
6. **Native Akita genericity is real but not sufficient.** A:akita-types/src/opening_claims.rs and extension_opening_reduction.rs, plus A:akita-verifier/src/stages/opening_claims/extension_claim.rs, support generic extension claims/reductions. A:akita-config/src/lib.rs checks declared/concrete extension degrees and requires `ExtField`, `FpExtEncoding`, and `MulBaseUnreduced` capabilities. The fp128 presets do not instantiate E.
7. **Existing subfield encoding is not the selected full-ring lift.** [A:field_reduction.rs](https://github.com/LayerZero-Labs/akita/blob/83574331d4e51f8cce1d8689d05592fa4ef4c138/crates/akita-types/src/field_reduction.rs) defines `FpExtEncoding` to mean coordinates in the specific ring-subfield basis consumed by `psi_embed`/`embed_subfield`; implementations include default `Ext2<F>` and tower types. Giving arbitrary nonresidue-5 coefficients that marker would assert an unproved embedding. SECURITY_PROFILE instead calls for scalar extension of the full S128 carrier: two complete S planes, 256 K coordinates per partial, same folding unit, no extra source plane. That needs its own source/query/receiver path; existing EOR support is not that API.
8. **Pending cut and acceptance.** `prove_stage8` currently returns `PCS::Proof` after full native batch opening. Its verifier counterpart performs full opening validation. A proposed pending frontend must preserve all metadata/presence/role/packing checks and return verifier-derived E obligations before PCS, not report complete-proof success. Endpoint/multipoint normalization and native accumulation/final decision remain additional interfaces, not existing behavior discovered here.

## 7. Lowering contracts and resolved source obligations

The [exhaustive reconstruction audit](AKITA_INSTANCE_ACCUMULATION_FRONTEND_DESCENT.md) now supplies the following semantic-descent and exceptional-point lemmas. Implementation must conform to those lemmas; the larger field alone remains insufficient.

* **Source descent/coverage:** the typed dependency DAG reconstructs every execution-relevant semantic table over K from the original K leaves and public data. E-valued partial bindings, staged bytecode combinations and uni-skip values are deterministic protocol intermediates, not new execution witnesses. Complete source-linked extraction trees and every enforced alias are necessary; arbitrary existential E auxiliaries still do not descend.
* **Evaluation compatibility:** prove for each dense/one-hot/packed/shifted/precommitted source that mixed K→E evaluation and partial binding equal the extension of its original Boolean-table MLE. Include bit order, prefix zero padding, lane layouts, source reuse and physical domain sizes. Fixed-table implementations need their actual Boolean-table/MLE equivalence, not a newly substituted lookup relation.
* **Stage extraction/lowering:** the source audit gives local backward-interpolation lemmas, exact degree/alias coverage, and total denominator branches. [The named segment-consumer replacements](AKITA_INSTANCE_ACCUMULATION_SEGMENT_LOWERING.md) extend the K recurrences using authenticated K endpoints, change the bytecode entry to the segment start, and apply global initialization/final I/O only once. Preserve those exact formulas and point identities in the symbolic and optimized implementations.
* **Original-handle opening:** show every final E obligation refers to the same K commitment/source, including full-field RAM endpoints and source-domain predicates. No commitment homomorphism, replacement E commitment, recomputed canonical source or reduced scalar-only partial is a substitute.
* **Actual sampler/manifest:** [the global manifest](AKITA_INSTANCE_ACCUMULATION_GLOBAL_MANIFEST.md) specifies all new scalar/vector/selector/native/final families, bounded unbiased samplers and an explicit fixed-polynomial tree ceiling. The immutable frontend ledger supplies the existing site order/degrees. The complete implementation must emit/check those descriptors and use E at every algebraic site; unchanged 16-byte sampling is not covered.
* **Same relation, conditional concatenation:** on extracted K tables, use the pre-existing legal-partition/endpoint recurrence argument. Do not strengthen it to emulator equivalence, new halt recognition, canonical u64 intermediate states, exact advice-tape semantics, or unbounded recursion. A full trace followed by a legal partition remains an allowed witness route.
* **Physical main holes:** semantic Booleanity leaves omitted address-zero source cells unconstrained. [The main-source reuse construction](AKITA_INSTANCE_ACCUMULATION_MAIN_SOURCE_REUSE.md) explicitly registers their zero predicate and strengthens the column-specific inactive-zero masks. Only with that coverage and the same-source trees may the extra full-main Boolean prefix be removed.

**Bottom line:** the inspected dependency graph gives no algebraic need to enlarge K source tables or change the whole-run execution relation. Semantic descent and inspected exceptional branches now have source-backed lemmas. Mixed-field APIs, original-handle queries, exact revised consumers and checked native ownership still need implementation. The current Jolt/Akita binaries do not already provide the proposed protocol.

**Observed work:** immutable source/specification reads and searches only. No source/document edits, branches, builds, tests, formatters or timings; test files were inspected, not run. This report does not certify compilation, end-to-end extension support, a completed manifest, 128-bit security, or performance parity.
